# Release provenance

Future Maven publications produce a Sigstore-signed in-toto statement covering
all four modules' binary JARs, source JARs and POMs. The publisher first builds,
tests, uploads and byte-compares the public Maven artifacts. Only then does it
sign their SHA-256 digests with GitHub Actions' short-lived OIDC identity.
The attestation is stored in GitHub's attestation service. A separate job attaches
the Sigstore bundle, signed DSSE envelope and subject checksums to the existing
GitHub release without replacing assets.

This applies to releases built with a publisher whose signing step succeeded.
**Versions 0.10.0, 0.11.0 and 0.12.0 have no such build attestation.** 0.10.0 predates
the signing step. In 0.11.0 and 0.12.0 the publisher signed but GitHub's attestation
service rejected the statement (`unsupported build type`, see
[predicate type v1](#predicate-type-v1)), so no bundle was retained or attached. Their
Maven bytes and historical evidence remain unchanged; the gap is not backfilled.
Local `publish.sh --publish` does not obtain GitHub's signing identity.

## Predicate type v1

The statement is signed with predicate type
`https://github.com/elide-dev/trufflecel/blob/main/docs/PROVENANCE.md#predicate-v1`.
Its body is shaped like a [SLSA v1 provenance](https://slsa.dev/spec/v1.2/build-provenance)
predicate but is deliberately **not** published as `https://slsa.dev/provenance/v1`.
GitHub's attestation service rejected that predicate type with this project's
`buildType` (`unsupported build type`; the rule is not documented). The one GitHub
`buildType` we know of describes a top-level workflow with a fixed parameter set and has
no place for the release version or the source tag's commit. Consumers must not treat
this statement as SLSA-conformant provenance or infer a SLSA level.

## Build type v1

Build type identifier:
`https://github.com/elide-dev/trufflecel/blob/main/docs/PROVENANCE.md#build-type-v1`.
The predicate body follows the SLSA v1 provenance layout, with these
project-specific semantics:

| Field | Meaning |
| --- | --- |
| `externalParameters.version` / `ref` | Requested immutable Maven version and its `refs/tags/vVERSION` source tag |
| `resolvedDependencies[0]` | The actual checked-out tag's Git commit; verified against VERSION, the release manifest and main ancestry |
| `internalParameters.workflowRef` / `workflowSha` | GitHub's workflow context, which can differ from the checked-out source tag during manual publication |
| `runDetails.builder.id` | The main-branch Maven publishing workflow |
| `runDetails.metadata.invocationId` | Workflow run and attempt that built and verified these bytes |
| Statement subjects | SHA-256 of each of the twelve Maven files; mutable Maven discovery metadata is excluded |

The publisher invokes `bazel test //...`, builds `//tools/release:publications`
with the release version, and stages files using `tools/release/maven_repo.py`.
Toolchains and dependencies come from the source revision's pins and lockfiles.
BuildBuddy can execute and cache actions; this statement does not enumerate
every transitive build input, prove an independent rebuild or claim a SLSA level.
The predicate is generated by repository-controlled code in the publishing job.

## Verify a downloaded artifact

Use a current [GitHub CLI](https://cli.github.com/manual/gh_attestation_verify).
For a release that includes provenance, download its bundle and verify each JAR
or POM you intend to use:

```sh
gh release download "v$version" --repo elide-dev/trufflecel \
  --pattern trufflecel-provenance.sigstore.json
gh attestation verify "trufflecel-core-$version.jar" \
  --repo elide-dev/trufflecel \
  --signer-workflow elide-dev/trufflecel/.github/workflows/publish.maven.yml \
  --predicate-type https://github.com/elide-dev/trufflecel/blob/main/docs/PROVENANCE.md#predicate-v1 \
  --bundle trufflecel-provenance.sigstore.json \
  --format json > verified-provenance.json
```

Verification must succeed before trusting the statement. Inspect the verified
predicate: its version, source tag and `gitCommit` must match the release you
intend to deploy. The signing workflow's main-branch commit alone is not the
artifact source identity. Unsigned checksum files are useful for integrity
checks but do not replace signature, identity and source verification.

## Failure recovery

Signing follows public-byte verification. A signing outage can therefore leave
valid published Maven bytes without an attestation; treat release qualification
as incomplete. Do not rerun publication over an existing immutable version or
manufacture replacement build evidence. Preserve the original run's build outputs
and logs, investigate the failed signing step, and document the gap if authentic
evidence cannot be recovered. The next release must pass the full pipeline.

If only attachment fails, rerun the failed attachment job or attach the existing
bundle from that run's `maven-provenance-VERSION` artifact. Do not overwrite
existing assets. The build job has attestation/OIDC permissions; only the
attachment job has repository-content write permission and it checks out no code.
